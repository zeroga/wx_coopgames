# 公共数据包 AI 维护规范

> 适用范围：AW 以及后续加入本项目的车辆、舰船、装备、科技线、活动目录等**公共游戏资料模块**。  
> 目标：让新的程序员或 AI 在不了解全部业务代码的情况下，也能安全、可追溯地更新数据包，而不会把推测、旧资料、生成文件误当成事实来源。

## 1. 核心原则

本项目的数据维护与小程序功能开发分离。数据维护任务默认只修改公共资料及其证据、生成物和发布元数据，不修改玩家/团队存档，不顺带调整 UI、交互、数据库权限或业务逻辑。

必须遵守以下规则：

1. **Git 中可审查的数据与证据是维护基准。** Supabase 是运行环境，不是唯一事实来源。
2. **未知就是未知。** 未找到、未看到、第三方未记录，都不能解释成“游戏中不存在”；应保留 `null`、`unknown`、待核实状态或已有值。
3. **不根据现实武器、同系列车辆、命名习惯、相邻科技线或其他游戏版本推断当前游戏数据。**
4. **生成文件不能手工改。** 必须修改其上游可维护输入，再运行仓库内生成器。
5. **稳定 ID 不随意重建。** 已存在实体的 UUID / slug / natural key 应保持稳定；遇到冲突先报告，不通过生成新 ID 绕过唯一约束。
6. **数据更新默认不直接写正式数据库。** 不把数据包挂到 migration、部署任务或自动导入脚本；需要数据库写入时应另立明确任务，并先核对目标库真实状态。
7. **公共资料与私有存档严格分离。** 数据包不得包含玩家码、团队码、玩家/团队计划、真实用户数据、服务端密钥或其他私有信息。
8. **每次修改必须可追溯到来源、核验时间和变更原因。**
9. **保持最小变更。** 数据任务不要顺带“清理”无关字段、重排 ID、格式化整库或重写未涉及实体，否则会破坏审查价值。
10. **发布前必须重新生成并验证，不接受“只改最终 JS/JSON 看起来能用”的交付。**

## 2. 数据分层

每个模块都应把数据至少分成下面四层。具体文件名可以不同，但职责不能混合。

### 2.1 原始/规范化数据源

这是可以人工或 AI 维护的实体数据与关系数据，例如车辆、舰船、武器、弹药、科技线和解锁条件。

要求：

- 保留稳定实体标识；
- 保留来源字段、核验状态和核验时间；
- 数值单位统一；
- 枚举值使用模块数据契约中的定义；
- 缺失值显式保留，不用默认值掩盖未知；
- 不能因某个展示页面暂时不用某字段就删除它。

### 2.2 证据与覆盖层

用于保存“原始资料不完整，但已有新的可靠证据”的修正，例如游戏内截图确认的科技树边、官方公告确认的特殊弹药类型。

覆盖层只允许修正证据能够证明的内容。  
例如一张科技树总览能证明车辆 A → B 的可见关系，不等于能证明 XP、升级节点、Token 数量和隐藏门槛。

证据应至少记录：

- 来源类型；
- 来源位置（URL、文件、截图说明或 Issue）；
- 核验日期；
- 能证明什么；
- 不能证明什么；
- 对应实体或关系；
- 核验状态。

### 2.3 生成产物

小程序内置目录、压缩包、发布 bundle、manifest、hash 等都属于生成产物。

生成产物必须能通过仓库脚本从上游数据重建。  
任何带有“Generated by”“Rebuild with”或同等说明的文件都禁止直接手工修值。

### 2.4 运行时私有数据

玩家资产、个人计划、团队计划、自定义前置、职责、备注、团队码等属于运行时私有数据。

公共数据更新任务不得：

- 导出或写回这些数据；
- 以公共数据更新为理由重置存档；
- 根据个人计划反向修改公共事实；
- 把维护者临时测试数据放入正式资料包。

## 3. 来源与证据规则

### 3.1 允许使用的来源

应优先使用能够直接证明目标字段的来源：

- 当前游戏客户端中的实际内容或维护者提供的游戏内截图；
- 游戏官方 API、官方数据库、官网公告、开发日志；
- 已明确记录来源和版本的可靠第三方资料；
- 现有仓库中已核验的资料和证据记录。

第三方资料可以用于发现候选值，但如果它与当前游戏表现冲突，不能覆盖更直接的当前版本证据。

### 3.2 禁止的推断

以下做法不能作为发布数据依据：

- “现实中这种导弹通常是 HEAT，所以游戏里也是 HEAT”；
- “上一辆车有烟幕，所以同系列下一辆也应该有”；
- “Wiki 没写，所以该能力不存在”；
- “名字包含某后缀，所以一定属于某弹药类型”；
- “科技树位置看起来相连，所以一定存在完整研发前置”；
- 用其他服务器、旧版本、测试服数据无标记覆盖当前正式服数据。

如果只有推测，可以写入待核实清单，但不能作为已确认值发布。

### 3.3 版本和时间

至少区分：

- **数据 schema 版本**：客户端能否解析；
- **资料版本**：本次数据发布版本；
- **source checked time**：原始资料最后核对时间；
- **published time**：数据包发布时间。

“今天发布”不等于“所有字段今天重新核验”。

## 4. 标准 AI 更新流程

### 4.1 开始前

AI 必须先读取：

1. 当前目标分支；
2. 本文件；
3. 目标模块自己的 README / 数据说明；
4. 数据契约或 schema；
5. 该模块的生成脚本；
6. 当前待核实 Issue / 核验清单；
7. 当前发布版本和生成物说明。

不得只打开最终 `catalog.js` 或一个页面组件就开始改数据。

### 4.2 确定变更范围

先列出本次实际要处理的实体和字段，例如：

- 新增 3 辆车；
- 修正 12 条弹药分类；
- 更新 6 条科技线关系；
- 补 2 个 Token 来源；
- 删除 1 条已确认不存在的旧关系。

对于“整库更新”，也应先明确来源覆盖范围和无法覆盖的部分。

### 4.3 修改上游数据

只修改可维护输入和证据层。

遇到以下情况应停止自动补全并记录为待处理：

- 同一实体有多个冲突来源；
- natural key 与既有 ID 不一致；
- 来源只能证明一部分字段；
- 新数据需要新增 schema 字段或枚举；
- 删除旧数据但没有明确证据证明它已失效；
- 无法判断单位或版本。

### 4.4 数据校验

至少检查：

- 主键 / 唯一键无重复；
- 外键和实体引用不悬空；
- slug / code 稳定；
- 枚举值合法；
- 数值单位正确；
- 等级、Tier、数量等范围合理；
- `null` 与“0 / false / none”没有混用；
- 科技树无意外自环或明显断链；
- Token 生成与消耗引用存在；
- 删除实体前确认没有其他关系仍引用它；
- 新增字段不会破坏旧客户端 schema。

校验失败时不得通过删除约束、关闭外键或跳过生成器来继续发布。

### 4.5 重新生成

使用仓库已有脚本生成客户端目录、压缩包、manifest 和线上发布 bundle。

生成后必须检查 Git diff，确认：

- 生成物变化与上游修改一致；
- 没有大面积无关重排；
- 版本号正确递增；
- hash / counts 与实际内容一致；
- 没有混入私有数据。

### 4.6 测试

数据任务至少需要通过该模块已有的数据检查和静态检查。  
如果模块提供客户端编译测试，也应执行。

不能用正式库现有业务数据做破坏性事务试验。数据库导入验证只能使用隔离环境或合成数据。

### 4.7 交付报告

每次数据更新必须给出一份短报告，至少包含：

- 本次资料版本；
- 新增 / 修改 / 删除的实体和关系数量；
- 使用的来源和核验日期；
- 哪些数据仍未核实；
- 修改的上游文件；
- 自动生成的文件；
- 执行的生成命令；
- 执行的验证命令与结果；
- 是否涉及 schema；
- 是否涉及数据库写入；
- 是否已发布线上资料包。

不能只写“数据已更新”。

## 5. 变更分类

### A. 普通数据修正

现有 schema 已能表达，只修改实体或关系值。

处理方式：修改上游数据 → 校验 → 重新生成 → 发布新资料版本。

### B. 新增实体

例如新车辆、新舰船、新武器。

除普通校验外，必须确认：

- 稳定 ID / slug；
- 所属分类；
- 所有必填关系；
- 未知字段仍明确保留未知；
- 不因资料不全而复制相似实体的数据。

### C. 删除或失效

删除风险高于新增。只有来源能够明确证明实体/关系已移除或失效时才删除。

如果只是暂时无法确认，应标记状态，不直接删掉历史数据。

### D. schema 变化

如果新资料无法用现有字段表达，不要把复杂内容塞进备注字段规避 schema。

应先形成 schema 设计任务，明确：

- 新字段 / 表 / 枚举；
- 旧客户端兼容方式；
- 数据迁移方式；
- 新旧资料包 schemaVersion；
- 发布顺序。

schema 变化与纯数据更新应尽量分开审查。

## 6. 数据版权与素材边界

本项目维护的是结构化事实数据和必要的来源说明，不应把第三方网站内容整页镜像进仓库。

AI 更新时：

- 不复制长篇攻略、文章正文或受版权保护的大段描述；
- 不把第三方图片批量打包为项目资源，除非已有明确许可和专门方案；
- 可以保存事实字段、短来源说明和来源 URL；
- 抓取第三方站点前应确认其稳定性和使用边界；
- 某个第三方站点只能作为候选数据源时，应保留可替换性，不让客户端直接依赖该站点。

## 7. AW 当前实现

AW 是本规范的第一套实际实现。当前 PR #8 分支为：

`feat/aw-catalog-fleet-v1`

### 7.1 AW 可维护输入

当前主要输入包括：

- `data/aw/AW_catalog_manual_data.zip`  
  包内 `source/catalog_snapshot.json` 保存公开目录快照。不要直接修改 ZIP 二进制；需要修基础快照时，应解出 source JSON，在工作副本中修改，再重新生成 ZIP。
- `data/aw/schema_data_contract.json`  
  数据包列、生成列、唯一键、主外键等结构契约。
- `data/aw/tech_tree_ingame_overrides.json`  
  游戏内科技树截图确认后的覆盖层，只修正证据明确支持的关系。
- `miniprogram/data/aw/ammo-classification.js`  
  弹头分类与证据补充。未知 ATGM 继续保持 unknown / needs_ingame_check。
- `miniprogram/data/aw/presentation.js`  
  只保存已明确核实的展示关系，例如互斥武器组；不能仅凭武器名或升级关系推断。

AW 当前基础快照仍存在待游戏内核实和缺失字段，因此更新任务不得把“没有记录”解释成“没有能力”。

### 7.2 AW 生成产物

以下文件属于生成/发布产物，原则上不要直接手改：

- `miniprogram/data/aw/catalog.js`
- `miniprogram/data/aw/release.js`
- `supabase/functions/aw-catalog/release.json`
- `data/aw/AW_catalog_manual_data.manifest.json`
- 重新构建后的 `data/aw/AW_catalog_manual_data.zip`

### 7.3 AW 基础生成流程

基础快照发生变化时，先准备修改后的 `catalog_snapshot.json`，再重建手动数据包：

```bash
python tools/build_aw_manual_data_package.py \
  --source /path/to/catalog_snapshot.json \
  --contract data/aw/schema_data_contract.json \
  --output data/aw/AW_catalog_manual_data.zip
```

然后重建小程序目录：

```bash
python tools/build_aw_miniprogram_catalog.py
```

只修改科技树覆盖层时，也应重新运行上述小程序目录生成命令。

发布线上资料包时：

```bash
node tools/build_aw_catalog_release.js YYYY.MM.DD.N ISO_TIMESTAMP
```

其中 `YYYY.MM.DD.N` 同日序号递增。内容变化必须产生新资料版本，不能用同序号覆盖不同内容。

详细线上发布行为见：

`docs/aw/catalog-updates.md`

AW 数据库空表与手工导入约束见：

`docs/aw/README.md`

### 7.4 AW 禁止事项

AW 数据更新任务默认禁止：

- 直接从正式 Supabase 表反向生成并覆盖 Git 基准；
- 直接修改 `catalog.js` 代替修改上游数据；
- 因 Wiki/官网未写而删除能力；
- 根据现实武器知识补弹头；
- 根据科技树视觉位置补完整 XP / 模块 / Token 条件；
- 自动执行全包数据库导入；
- 重建已有 UUID；
- 把玩家/车队规划写进公共资料；
- 为了数据更新顺带修改车辆卡片 UI 或车队业务逻辑。

## 8. 后续模块接入要求

以后新增战舰世界或其他资料模块时，应在开始批量录入前先补齐最小数据维护结构。

每个模块至少应明确：

- 模块 ID；
- 数据 schemaVersion；
- 可维护源数据路径；
- 证据 / override 路径；
- 生成产物路径；
- 生成命令；
- 校验命令；
- 资料版本格式；
- source checked time 的含义；
- 发布方式；
- 数据源优先级；
- 未知值表示方式；
- 稳定 ID / natural key 规则；
- 哪些内容明确不进入公共包；
- 哪些文件禁止手工修改。

推荐目录形式：

```text
data/<module>/
  README.md
  schema_data_contract.*
  source/
  overrides/
  evidence/

tools/
  build_<module>_...
  check_<module>_...

miniprogram/data/<module>/
  <generated catalog>
  <generated release metadata>
```

AW 当前历史结构不要求为了统一目录立即迁移；新模块优先按该结构建立。

## 9. 给其他 AI 的标准任务开头

以后委托 AI 更新某个模块数据时，可直接使用下面的任务开头：

```text
你负责更新 wx_coopgames 的 <module> 公共数据包。

开始前必须阅读：
1. docs/data-package-maintenance.md
2. data/<module>/README.md（或该模块现有数据说明）
3. 当前 schema / data contract
4. 当前生成与校验脚本
5. 当前待核实 Issue / 核验清单

要求：
- 只依据可追溯证据修改数据，不推测补全；
- 未知字段保持未知；
- 不直接修改生成文件；
- 不修改玩家/团队存档；
- 不直接写正式数据库，除非任务明确要求；
- 保持现有稳定 ID；
- 先修改上游数据，再运行生成器和校验；
- 最终给出变更数量、来源、未核实项、生成文件、测试结果和资料版本。
```

如果任务内容与本规范冲突，以用户在该次任务中的明确指令为准，但 AI 必须在交付中指出偏离了哪一条数据维护规则。
