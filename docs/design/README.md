## 原型的用途与验收标准

原型主要用于维护页面内容和明确交互逻辑。当用户难以用文字准确表达操作方式、页面关系或状态变化时，用可编辑原型辅助说明。

**原型以内容和交互逻辑一致为标准，不要求像素级还原当前代码。**

核对重点：

- 页面包含哪些信息、字段、标签和操作入口，以及它们的关系。
- 操作对象是谁、作用范围是什么，例如当前平台、当前玩家或整个团队。
- 点击后的去向、展开 / 折叠、选择、编辑、保存、取消和必要的确认逻辑。
- 会影响用户判断或操作结果的状态与规则，例如已拥有 / 计划、未知数据、完成条件。

字体、颜色、边距、控件高度、圆角等视觉细节不要求逐项与代码相同。只有妨碍阅读、掩盖必要信息或让交互产生歧义时，才需要修正；不为消除一般视觉差异而持续同步两边。

原型不需要模拟真实云端读写，也不需要穷举所有状态组合。未画出的行为可以在 Issue 或设计说明中用文字明确。静态图没有表达某项行为，不代表代码中没有该行为；影响内容或操作结果的冲突仍需核实。

## 开发时如何使用原型

1. 先明确需求内容和交互逻辑；文字足够表达时，直接使用 Issue / 说明。
2. 当前原型暂停：文字不足以表达时，直接在小程序中制作交互供本地测试；恢复原型设计后再用原型辅助说明。Issue #3、#5 无原型前置要求。
3. 实现后的核对以内容和交互为主，不把视觉一致性作为完成条件。
4. Figma 可以表达尚未实现的设计，需在说明或版本记录中区分“已实现”和“待实现”，避免误认成当前代码行为。

原型只表现主要场景时，应注明覆盖范围；不要把未画出的状态认定为功能缺失，也不要据此宣称所有状态已经过核验。

## 版本管理

原型采用两层版本管理。

### Working Copy

`Working · GitHub main` 是唯一允许持续修改的工作页。

恢复原型设计后，日常调整在该页进行；暂停期间，最新设计以 Issue 与 Git 中的小程序页面为准。

### Snapshot

在页面内容或交互逻辑发生有意义的改动、形成可确认版本时，在同一 Figma 文件中新建快照页。修改 Working Copy 前保留最近一个可恢复的版本；单纯代码提交或一般视觉差异不要求新增快照。命名格式：

```
vYYYY-MM-DD · <git-ref>@<short-sha> · <label>
```

当前首个快照：

```
v2026-10-03 · main@e660d7e · baseline
```

快照页建立后视为只读基线，不在其上继续日常编辑。后续设计从 Working Copy 继续演进。

每个快照同时登记到 `paths.json`，记录：

- Figma page node id
- 主要 screen node id
- 对应 Git commit
- 版本日期
- 版本说明，包括本次内容 / 交互变化及已实现 / 待实现状态

这样即使 Figma Working Copy 后续发生大量变化，也能准确恢复“某一提交当时对应的设计”。

> 不把 `.fig`、`.mg` 等二进制文件放进 Git 作为设计版本基准。Figma 云端保存设计实体，Git 保存定位、对应关系和版本索引。

## GitHub 与 Figma 的职责

### GitHub

GitHub 是以下内容的正式版本基准：

- 小程序实际运行代码
- 页面业务逻辑
- 云端 / 本地状态读写
- 数据文件与数据库结构
- 已经实现并可发布的功能

### Figma

Figma 是以下内容的设计工作区：

- 页面内容与信息层级
- 操作入口、页面关系和交互状态
- 难以用文字表达的交互方案
- 代码尚未实现的内容与交互设计

页面布局和视觉样式可作为实现参考，但不作为逐像素验收标准。

因此 **Figma 可以有意领先于 Git 代码**。差异本身不等于错误。

## Work 核对代码与原型时的规则

1. 先读取 `docs/design/paths.json`；若 `design_workflow.status` 为 `prototype-paused`，只在明确要求历史比较时读取 Figma，不阻塞小程序开发。
2. 明确比较的是 `working` 还是某个 `snapshot`，不要默认使用旧截图。
3. 代码侧读取目标分支 / commit 的真实文件。
4. 原型侧读取 JSON 指向的 Figma page 和 screen node。
5. 按 screen 的 `source_paths` 比较，不跨页面猜对应关系。
6. 优先核对内容和交互逻辑；发现差异后先分类，不自动覆盖任意一边。
7. 一般视觉差异只记录，不作为基线失效或开发阻塞的理由；影响阅读、信息完整性或交互理解的差异单独指出。
8. 不把原型缺少动态状态等同于代码缺少功能。对未表达或存在歧义的交互，读取代码 / Issue；有必要时再补文字或原型说明。

差异分类：

- `design-ahead`：Figma 已设计、代码尚未实现。
- `code-ahead`：代码已有、Figma 尚未表示。
- `visual-drift`：同一功能的布局、颜色、尺寸等出现视觉偏差，默认不要求修复。文案若改变含义或丢失必要内容，应作为内容差异核对。
- `behavior-only`：代码中的业务逻辑 / 状态变化未由画面直接表现，可用文字说明；若与原型已明确的交互相冲突，仍需处理。
- `data-only`：属于动态数据内容，不要求原型逐条同步。
- `intentional`：已确认的主动差异，不应自动修复。

默认核对任务只输出差异报告。除非任务明确要求，不因为发现差异就自动修改 Git 或 Figma。
