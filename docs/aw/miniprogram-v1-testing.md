# AW 小程序交互测试版（Issue #3 / #5）

当前暂缓 Figma 原型，直接在小程序里设计和验证交互。这个版本用于本地测试反馈，不将两个 Issue 提前标记为完成。

## 本地启动

1. 拉取 PR 分支 `feat/aw-catalog-fleet-v1`。
2. 复制根目录 `project.config.example.json` 为 `project.config.json`，填写自己的微信 AppID。
3. 在微信开发者工具中导入仓库根目录，确认 `miniprogramRoot` 是 `miniprogram/`，启用增强编译。
4. 从首页进入 **Armored Warfare**。默认使用随包公开资料和本地存储，不需要新建表或执行 SQL。
5. 在“车队 → 玩家”添加测试玩家，再在“职责管理”建立自定义职责；从车辆详情登记车辆。

资料快照来自仓库已有手动数据包，时间为 2026-10-01，含 298 辆车和现有全部公共实体 / 关系。不是新采集或已经完成游戏内核验的数据。“刷新云端资料”只读取公共资料表；失败保留当前资料。

随包资料是生成文件，不能手改。运行 `python tools/build_aw_miniprogram_catalog.py` 可从数据包确定性再生成 `miniprogram/data/aw/catalog.js`。列数组与字符串字典只改变编码，保留原始空值、字段、来源和 ID。没有新增图片或 npm 依赖。

## 页面与交互

| 页面 | 交互 |
| --- | --- |
| 车辆资料库 | 搜索、五组筛选入口、可移除条件标签、分页、最多两条车队摘要 |
| 车辆详情 | 身份与能力、2×2 核心性能、配置分组、弹药展开、配件、来源、快捷编辑 |
| 科技树 | 搜索定位、获取路线与条件、已选路线、公开前后显示关系 |
| 车队总览 | 职责 → 主力 / 备选 / 过渡 → 车辆 → 玩家；显示目标与来源 |
| 玩家 | 新增、改名、顺序、停用 / 恢复、当前玩家偏好、车辆与 Token 编辑 |
| 职责管理 | 自定义名称 / 说明、拖动或上下移动排序、确认删除职责关联，保留资产 |
| 获取规划 | 每玩家目标、递归前置、多路线选择、条件确认、Token 总量与过程检查 |

玩家状态 `owned / planned`、自定义职责、职责级别 `primary / backup / transition` 独立存储。玩家以稳定 ID 为键，改名不改变车辆关系。当前玩家是本地偏好，不是权限身份。

保存车辆和重算前置先在内存中的完整副本完成，再一次写入本地。取消编辑不写入。手工与科技树依赖分别保存，可引用多个目标；取消目标只清理自动职责 / 依赖，保留玩家资产。移除资产时，仍被其他目标需要的资产会重新建立为计划。

科技树仅使用 `unlock_paths / unlock_requirements` 的明确前置，不把 `vehicle_progression_edges` 的显示关系当成完整获取条件。多条完整路径需选择；不完整路线、循环、其他条件和缺资料持续显示待确认。已拥有的状态不会被自动改回计划。

Token 按玩家全部正式目标合并检查，共享节点和奖励只计算一次。当前持有 + 确认获取必须严格大于消耗；每步先消耗再领取奖励，后续奖励不能解决前一步的不足。奖励需要公开核验记录且用户确认获取时点；已拥有车辆的过去奖励只应填入当前持有，不重复计入预计获取。条件开关表示用户核实可满足，不修改公开资料。多目标的步骤顺序目前按目标和各已选路线的依赖顺序展开，不自动搜索其他可执行顺序。

## 建议本地验收

- 搜索 Boxer RIWP，切换五种配置，展开弹药；核对未知参数隐藏、默认 / 研发 / 待确认标签。
- 组合等级 / 车型筛选；组合“ATGM + 攻顶 + 自导 + 穿深”，核对同一枚弹药匹配；切换出厂能力口径。
- 新建玩家和两个职责，将同辆车设为某职责主力、另一职责备选；改名后检查记录仍在。
- 新建两个计划目标，查看已知前置、手工过渡的多目标选择，取消一个目标后检查共享前置和已有资产保留。
- 选择需要 Token 的已知路线，测试持有量等于消耗量时不满足，增加持有量后检查总量与过程。
- 对缺完整路径车辆确认“待补全”，不应显示确定可完成；确认奖励触发条件前不应计入可用余额。
- 测试弹层取消、职责删除确认、玩家停用与恢复、退出重进后本地记录保留。

真实资料目前多数获取路线不完整，因此完整闭包、多路线和 Token 临界场景另由合成数据的自动测试覆盖。不会为演示完整链而伪造真实车辆资料。

## 共享与迁移范围

此交互版沿用已有 `coop_profiles` 和 `game_states` RPC。先在 SnowRunner 页连接共享团队码；AW 本地缓存按 profile 隔离，当前玩家偏好同样隔离。进入车队后载入云端，再编辑并手动上传。AW 状态保存于 `game_key = aw`，不写旧 `aw_fleet_plan_items`。

玩家显示名称通过共享 profile 的 `users[稳定ID]` 同步；停用和顺序存在 AW 测试状态中。SnowRunner 当前仍只展示 A / B 两个槽位，尚未改造为任意人数的全游戏玩家管理页面。

上传前检查云端 version；冲突保留本地内容，可复制备份。**这个接口没有服务端 compare-and-swap，也没有把状态保存与 profile 名称同步合为一个事务。多人同时上传仍可能产生竞争；此版用于单人本地交互验收。**正式共享交付需进一步实现服务端事务、稳定成员管理、并发冲突处理和正式数据迁移验收。

“读取旧计划”只读旧 RPC，导入有效状态为资产；保留旧 ID、role、priority、status 和原始记录在 `legacyAudit` 中。`abandoned` 等状态只留审计，不自动生成活动资产；旧 role 不猜测为新职责。重复导入幂等。不删除旧表，不自动运行迁移。

本次不执行正式库 SQL，不修改真实团队计划，不宣称已经完成正式库迁移或多人并发验收。
