# AW 线上资料发布与离线缓存

客户端版本：`2026.10.04.5`。首次发布资料版本：`aw-2026.10.04.5-0541184c1191`。

## 客户端行为

进入 AW 首页、资料库、车辆、科技树或车队页时先显示本地资料，再异步检查版本；同一进程自动检查间隔 15 分钟，重复请求合并。无需玩家码也能更新公共资料。已有车辆编辑草稿时不触发页面自动读取；如果下载已经开始，新目录等待车辆编辑结束再切换。

AW 首页和车队页的“刷新”同时处理资料更新及存档同步。有已发布个人档/已连接车队时，存档仍先上传本地改动再下载；失败或版本冲突保留待上传内容。公共资料独立检查，因此存档冲突不会阻止资料下载，资料网络失败也不会阻止存档上传。失败会分别提示，不能显示成全部成功。

目录包包含全部公共目录表、弹头分类补充和有证据的互斥武器组。包括车辆、武器/弹药、能力、科技树、研发条件、Token 奖励与消耗关系；不会包含玩家码、车队码、玩家/车队计划、私有问题队列或私有原始快照。

下载前检查 schema/发布序号与表数量；下载后检查 SHA-256、字段完整性、数量及关联 ID。校验失败、请求失败、下载期间服务换版、缓存写入失败均不覆盖当前目录。旧版本不会覆盖较新缓存；同序号不同内容视为发布错误，必须发新序号。

缓存使用两个槽位，按 64,000 字符分块保存，最后写当前槽位指针。分块避免单项缓存大小限制，写到一半失败仍保留旧槽位。重启先完整校验缓存；缓存损坏或旧于随包版本时使用随包目录。资料切换只在内存重算自动过渡关系，不把更新当成存档编辑或自动上传。手工职责、资产、备注、路线选择及奖励/消费记录保持原样；未知门槛仍阻止完整路线判断。

界面分别显示代码测试版、资料版、资料包发布时间、原始快照核对时间，避免把新发布包解释为所有性能都重新实测。

## 数据维护与发布

1. 更新 Git 中可维护数据及证据，补充缺失数据应按 Issue #4 逐项核验。截图覆盖层 `data/aw/tech_tree_ingame_overrides.json` 仍独立于原始手动导入 ZIP。
2. 生成随包目录：`python tools/build_aw_miniprogram_catalog.py`。本版生成器同时修正 XM800T LAW 显示线和原已记录的前置车辆 ID；不将 XP/模块条件标记完整，不更改路线/条件 ID。
3. 生成发布包和客户端元数据，例如：`node tools/build_aw_catalog_release.js 2026.10.04.5 2026-10-04T04:41:54Z`。每次内容变化必须使用新的 `YYYY.MM.DD.N`，同日序号递增。只更新在线资料时也需提交生成的元数据/包，以便后续客户端内置基线一致。
4. 验证测试、编译、数据重建和完整性。提交 PR，追加当次实现及验证 comment。发布的是可审查的资料包，不从未导入截图修正的旧数据库直接生成，避免把旧前置关系重新下发。
5. 将 `supabase/functions/aw-catalog/` 中 `index.ts`、`deno.json`、`release.json` 发布为自有项目的 `aw-catalog` Edge Function。读取接口是 `/functions/v1/aw-catalog`；返回 manifest。带 `?bundle=1&version=<manifest.version>` 返回同一版本的完整包，换版时返回 409 让客户端重试。
6. 检查线上 manifest 与完整包 SHA-256、实际返回目录及错误路径，再让用户刷新。无需重新审核小程序即可获取与 schema 兼容的新资料。代码变更仍按根 README 的人工审核/PR 规则发布。

服务只支持 GET/OPTIONS，使用项目 publishable `apikey` 并在函数中验证。由于 publishable key 不是 JWT，`supabase/config.toml` 将此函数 `verify_jwt=false`；请求不发送 publishable Bearer token。函数不使用 service role、不访问数据库、不提供写接口。资料发行部署不会更改正式目录表或真实存档。数据库结构与初始手动导入方式继续沿用既有规则。
