# 微信合作游戏小程序 / wx_coopgames

用于管理合作游戏资料、团队计划与共享进度的微信小程序项目。

当前项目首先覆盖 **SnowRunner**，并正在加入 **Armored Warfare（AW）车辆资料库与团队车辆计划**。后续可继续扩展其他需要多人共享进度、车辆/装备计划或资料查询的游戏。

## 当前基准

小程序端当前以以下版本作为代码基准：

- **提交审核版：`coopgame-review-v3-collapse-full.zip`**
- 日期：2026-10-01
- 后续小程序修改均应从该版本进入 Git，不再以聊天附件或临时 ZIP 作为正式版本来源。

数据库当前使用 Supabase 项目：

- 项目名：`wx_coopgame`
- Git 仓库：`zeroga/wx_coopgames`

> Git 是项目代码、数据库结构变更和可维护数据文件的版本基准。  
> Supabase 是实际运行数据库，也是 AW 正式公共事实与证据的真源；资料维护通过可追溯的变更/审核/发布接口完成。

## 版本、体验版与正式审核

微信小程序正式发布需要人工审核。维护者会在审核通过后才合并对应 PR；审核期间 PR 保持开放，不提前合并 `main`。

- **最新待验收源码在 PR #8**，分支 `feat/aw-catalog-fleet-v1`。拉取此分支重新编译，当前代码测试版为 `2026.10.07.2`，人工上传可用版本号 `0.1.0-test.20261007.2`；此源码尚未上传体验版。
- Git 推送不会自动上传微信体验版：维护者仍需用微信开发者工具上传，并在微信后台设为体验版。`main` 对应已完成审核并合并的代码，不能用它判断最新体验版本。
- PR Conversation 采用**每次追加新 comment**记录版本、具体实现与验证结果，不覆盖历史 comment，也不把 PR 正文反复改成最新版本。实现问题应能追到对应 commit 和当次记录。
- Issue 正文可更新为当前需求或核验清单，不要求保留每次编辑的全文。

AW 资料与小程序代码分别发布：客户端内置初始资料包，自动检查自有 Supabase 资料发布服务，校验后缓存新资料；离线继续使用已缓存或随包资料。资料更新不改玩家/车队存档。当前为发布经过核验的目录包，不是让手机直连逐表查询或自动采集未核实数据。详细发布流程见 [AW 线上资料更新](docs/aw/catalog-updates.md)。其他 AI 的操作文档见 [AW 数据维护接口](docs/aw/catalog-maintenance-api.md)，手工 KEY 签发 SQL 与部署步骤见 [管理员说明](docs/aw/catalog-maintenance-admin.md)。

本次 `2026.10.04.7` 按 SnowRunner 现有设计语言统一 UI；代码已更新不代表微信体验版已上传。规范及逐页检查见 [全局 UI 整改记录](docs/ui-component-review-2026-10-04.md)。

## 功能范围

### SnowRunner

现有小程序主要提供：

- PC / 主机双页签
- 双成员团队资料
- 团队码共享合作档
- 赛季与区域推进清单
- 目标勾选、编辑、增删
- 车辆取得与成员分配
- 顺序调整
- S1–S19 赛季数据
- 本体区域独立记录
- 云端共享状态

团队数据模型同时作为 AW 团队车辆计划的基础。

### Armored Warfare

AW 模块目标包括：

- 浏览车辆资料
- 按等级、车型、经销商、国家等基础条件筛选
- 按 ERA、烟幕、步兵班等车辆能力筛选
- 按自导导弹、攻顶导弹等弹药能力筛选
- 按 AP 穿深筛选
- 查看车辆主要武器与弹药
- 查看可研发配件
- 查看完整科技树
- 查看车辆研发 / Token 解锁条件
- 使用现有团队码共享车辆计划
- 查看其他成员已经计划的车辆
- 后续扩展为车队组建器

AW 第一版不使用车辆图片作为核心数据依赖，也暂不加入主观评分。

AW 入口提供“车辆资料库、车队管理”两张模块卡片，科技树从车辆详情和获取规划进入。车辆资料先读取本地缓存，并自动检查线上资料更新。顶部车辆信息和车队状态常驻，其余模块独立折叠；展开武器模块后列出全部武器，每枚弹药收起为一行并可单独展开详情。自己的车辆登记使用职责标签。成员使用独立 `AW-M-` 存档码，车队使用 `AW-T-` 码读取团队。随后输入自己的玩家码识别身份，未入队先确认，已入队直接读取并显示退出；只能修改自己的车辆与职责。

Issue #3 / #5 的小程序交互测试版入口、运行步骤、改动记录与数据库过渡说明见 [AW 本地测试说明](docs/aw/miniprogram-v1-testing.md)。

## 数据与版本管理原则

公共游戏资料由其他 AI / 程序员维护时，统一遵守 [公共数据包 AI 维护规范](docs/data-package-maintenance.md)。该规范定义事实来源、未知值、稳定 ID、证据层、生成产物、校验、发布和交付报告要求；AW 及后续模块均适用。

### 小程序代码

小程序源码直接进入本仓库。

正式基准由 Git commit 确定，不再依赖“最新版 ZIP”作为长期版本判断方式。

### Supabase Schema

数据库结构变更应进入：

```
supabase/migrations/
```

长期规则：

1. 先形成可审查的 migration。
2. 再应用到 Supabase。
3. 应用后验证实际数据库状态。
4. Git 与线上 migration history 保持对应。

临时诊断 SQL 可以直接执行，但永久结构修改不能只存在于一次聊天任务中。

### AW 数据

AW 车辆、武器、弹药、科技树与解锁资料需要长期维护。

原则上：

- 原始 / 可维护数据应进入 Git。
- Supabase 作为运行时查询数据库。
- 单车修正应能通过 Git diff 追溯。
- “未采集到”不能被解释成“游戏中不存在”。
- 无法公开确认的数据保持未知或待游戏内核实，不猜测补全。

## 安全要求

本仓库为公开仓库。

禁止提交：

- Supabase `service_role` / secret key
- 私有数据库密码
- 微信平台私钥
- 用户真实团队码
- 其他访问令牌或账号密钥

前端只能使用适合公开客户端使用的配置，并依赖数据库端 RLS / RPC 做实际访问控制。

### AW 公共资料增量更新（2026.10.06.1）

本地始终保存完整 catalog；常规线上更新下载稳定键增量，在临时槽合并、校验结果 hash 并回读缓存后原子切换。没有直接 patch 或验证失败时回退最新 full，旧版始终保留。新车辆与关联资料在现有 schema 范围内仅发布资料即可进入列表、筛选、详情、科技树和规划，无需客户端再次发版。上传、拉取审核与确认发布可以交给不同 AI；服务器生成 patch，Supabase 保存完整发行与正式事实，Git 保留旧不可变历史基准。协议、命令、交接与部署说明见 [AW 资料更新](docs/aw/catalog-updates.md)。本次更新需要上传一次新客户端来启用增量机制；源码、生成物已准备不代表线上部署完成。

`catalog.js` 随小程序编译打包，手机不会访问 Git 下载 JS；在线资料由 Supabase `aw-catalog` 下发。正式增量基线须匹配按环境确认的部署记录，本地更新诊断区分待生效、生效和失败。本版新增数据库维护接口和手工 KEY 管理 SQL；快照的长期维护暂缓，旧 ZIP 用于初始化与历史复现。

### AW 前置配置（2026.10.04.6）

新登记的计划车辆默认为“无视前置”，不会自动加入科技线前置或 Token 来源车；黄色感叹号保留，并显示“需要前置”。点击感叹号，第一层只列出数据已知的获取路线及对应 Token 来源车辆；点“自定义前置”后才进入全部车辆搜索，可多选并单独标识。自定义配置只影响自己的规划，随个人存档自动上传、跨设备读取，公共目录与核验记录保持独立。

选择已知路线或自定义前置后才展开依赖。已忽略前置的未拥有车辆不会被推断为免费获取，也不计入可获取 Token 奖励；自定义车辆只有自身存在真实 Token 奖励数据才参与计算。已保存的旧路线选择继续保留，未选择路线的旧计划按忽略处理；取消弹层不保存。数据核验状态留在后台，车辆、弹药和科技树页面不再显示核验标签。
